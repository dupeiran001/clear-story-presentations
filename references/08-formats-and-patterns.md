# 08 — Choose the format-specific story, without becoming formulaic

Treat these as **diagnostic starting points**, not mandatory order/templates. In each case, identify the audience's actual question and evidence.

## A. Academic conference / research talk

**Question → stakes → genuine gap or obstacle → core insight → just enough method → discriminating experiment → findings → interpretation/limits → remembered message.**

- Don't copy Introduction/Related Work/Method/Experiments/Conclusion order mechanically.
- Prioritize the core mechanism and strongest evidence over exhaustive configurations.
- Make baseline comparisons and experimental conditions understandable.
- Distinguish novelty vs proven benefit vs speculation; related work should set comparison, not become an inventory.
- Worked running example often explains method better than full architecture copied from paper.
- Put formulas, ablations and failure cases likely needed for specialist Q&A in backup.

## B. Executive / leadership decision briefing

**Recommendation → why now → three strongest reasons if naturally grouped → alternatives + cost/risk → ask, owner, deadline, test.**

- No suspense hiding the recommendation. Start with current decision status.
- Distinguish information requested vs decision required.
- Cite denominators, baseline, operational trade-offs and uncertainty.
- Appendix can support readers who will scrutinize assumptions.

## C. Weekly/monthly status or project update

**Status vs goal → what changed → impact → drivers/blockers → decisions/owners/next checkpoint.**

- Show progress against the original plan rather than uncontextualized activity metrics.
- Keep red/yellow status honest; don't launder blockers through a “wins” list.
- Include slippages, impact, and what is needed from the audience.

## D. Product/business pitch

**Specific user/job → real pain and existing workaround → proposed change → representative workflow → proof → model/constraints → next ask.**

- Not all pitches need a personal founding anecdote or market slide.
- Avoid “huge TAM” disconnected from a practical segment; label forecasts.
- Demonstrations and authentic user evidence beat generic capability slogans.

## E. Technical deep dive / engineering design review

**Invariant/problem → constraints → design choices → algorithm/architecture → comparison → testing → failure modes → operational implications.**

- Make assumptions, interfaces, control/data flow and complexity explicit.
- Show at least one concrete end-to-end example.
- Make where the design differs from alternatives unmistakable.
- Organize hard trade-offs (latency, reliability, cost, maintainability) rather than one-sided advantages.

## F. Workshop / teaching

**Diagnostic puzzle → purpose → scaffolded concept → worked example → learner task → feedback → transfer challenge.**

- Make learners do something, not just watch.
- Segment by prerequisite level; introduce vocabulary close to use.
- Reserve time for practice; use a simple formative check before introducing the next concept.

## G. Public keynote / TED-like idea talk

**Relevant situation → surprising but true obstacle/insight → grounded examples → practical implication → thoughtful close.**

- The emotional arc must be **earned** by truth and lived details.
- Story is a means of explanation, not a replacement for evidence.
- Slides may be unnecessary. Avoid staged inspiration and forced “hero” narratives.

## H. Portfolio / case study / design critique

**Context and constraints → user problem → options → rationale → artifact/process → outcomes → limitations and learning.**

- Show actual work, not merely polished final shots.
- Explain decisions and rejected options; avoid portfolio-as-marketing with no reflection.

## I. Incident postmortem / safety review

**Impact → observation timeline → contributing mechanisms → detection gaps → recurrence risks → concrete preventive actions.**

- Keep causal language carefully grounded; distinguish hypotheses from confirmed root causes.
- Avoid blame theatre and false certainty.

## J. Sales enablement / client proposal

**Client-specific stakes → diagnosis → desired outcome → approach → credible case/evidence → trade-offs → process/decision.**

- Use customer's context and terminology; no generic service menu up front.
- Keep scope and pricing clarity where relevant; don't conceal constraints.

## K. Training / tutorial screencast

**Task → expected output → minimal prerequisites → real procedure → troubleshooting → recap.**

- Screen recording beats screenshots when interface movement is the concept; screenshots plus callouts can be better for stable steps.
- Test every stated step in actual tooling; version-specific UI claims may change.

## L. Document-to-deck transformation

Reverse-engineer the author's argument and reader dependencies, not just chapter list. Identify content to present vs cite vs omit. For policy/legal/financial/regulatory contexts, preserve exact condition wording and qualifications even when visual designs would prefer brevity. When precision cannot fit a slide, build a visual summary plus a readable appendix/handout.

## Cross-format question bank

- Which change in audience understanding justifies this slide?
- Is the conclusion explicit, or merely implied by data?
- What decision would be different if this point were wrong?
- What is the strongest alternative interpretation?
- Which claim deserves a counterexample or limitation?
- Does the format require speaker notes, read-alone documentation or a live walkthrough?
